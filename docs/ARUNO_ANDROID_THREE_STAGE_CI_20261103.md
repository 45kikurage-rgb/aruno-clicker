# ARUNO Android / GitHub Actions 3段階検証標準（2026-11-03）

対象: DPC、あるのティッカー（Aru-Tiker）、Aru-Click。ARUNOMATICなど他のAndroidアプリでも原則適用する。

## 目的
GitHub Actions のLinux runner時間を節約しながら、最終候補の安全確認を弱めない。**普段の変更で4種類のAndroidエミュレーターを毎回起動しない**。同じソース・同じ署名候補に対しての試験証跡を再利用する。

## 段階
1. **lightweight / 軽量**（全変更・PRの基本）: 変更対象の静的検査、ホスト単体テスト、画面・URLの契約テスト。署名鍵、エミュレーター、公開トークン、本番書込みを使わない。影響がないプラットフォームのテストは走らせない。
2. **targeted / 対象端末のみ**（UIやAndroid依存動作に変更があるとき）: 段階1の成功を前提に、変更に直接関係するAPIを**原則1種類**だけ選ぶ。DPC: Android9=API28、Android10=API29、Android15=API35、Android16=API36のうち該当するもの。実行済みのAPKを再利用し、再ビルド・再署名はしない。失敗なら原因を分析し、必要な対象だけ再試験する。
3. **full / 最終候補**（明示承認済みリリースのみ）: 凍結したソースcommitとAPK SHA256を指定し、DPCはAPI28/29/35/36を含む承認済みの全対象バージョンで試験。Aru-Tiker / Aru-Clickはその版のサポート対象と回帰リスクに応じた全マトリクスを実行。既存署名照合、更新互換性、公開物の再取得・一致確認は従来どおり省略しない。実機試験はエミュレーター成功と区別する。

## GitHub Actions の実装ルール
- **通常のpush/PRはlightweight**。複数エミュレーターの常時起動は禁止。段階2は対象APIを明示して呼び出す。段階3はリリース対象commit・承認参照・full指定が揃わなければfail-closed。
- 検証段階の決定は`ci/ci_tier_plan.py`を使い、APIマトリクスをハードコードで常時展開しない。`.github/workflows/aruno-ci-plan.yml`を再利用ワークフローとして呼び出せる。**このプランナーは試験実施ではなく試験計画のガード**。呼び出し元に実際のbuild/test/emulatorゲートを設置する。
- fullマトリクスを走らせるworkflowは、lightweight → targeted(必要な場合) → full の順にneedsを張り、前段失敗時に先へ進まない。必要なAPIが1件でも落ちれば公開を禁止する。
- 本番公開、署名、データ変更、既存の公開物の上書きには元の明示承認と独立照合を要求する。検証段階の変更だけで本番公開を自動起動してはならない。
- 同一source SHA / 同一APK SHAをキーに証跡再利用。失敗ジョブの再実行を優先し、無関係な成功済みOSテストを毎回やり直さない。原因不明の失敗をリトライだけで繰り返さない。
- workflowを新設/変更するときは、各段階の「対象API、見込runner分数、実際の実行分数、失敗再試験件数、公開の有無」を記録する。時間はワークフロー所要時間ではなく各jobの実行時間合計で測る。
- 既存のバージョン専用・署名済み配布ワークフローを一斉に書き換えない。**次の改修時に対象ワークフローへ段階制御を組み込み、リリース経路を保ったまま移行する**。過去の公開成功の証跡、Secrets、証明書、URLは維持する。

## 判断例
- 文章・UI余白のみ: lightweight。表示影響がある場合に限ってtargeted API1つ。
- Android9のHOMEや履歴カードの不具合: lightweight → API28 targeted。Android10独自の不具合ならAPI29。
- リリース確定後: frozen candidate と既存署名でfull。**fullを成功扱いする条件に全対象OSの成功と配布APKの同一性検証を含める**。

## 注意
`ci/ci_tier_plan.py`は計画作成・承認不足時の拒否だけを担う。実機・UI検証が完了したと表示してはならない。既存DPC code26〜29等の過去実行は変更せず、今後作成するワークフローから順次採用する。
